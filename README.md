# 电商仓配多平台对接与实施知识检索系统

面向国内电商仓配 ERP 与电商开放平台对接、实施上线及故障初判场景的垂直领域 RAG 知识检索系统。聚焦**订单同步失败、库存回写差异、电子面单取号与打印异常**三类高频技术支持问题，支持按**产品、平台、客户端版本**多维筛选，输出可追溯原文出处的排查结论。

- **业务背景与检索痛点**：仓配实施对接同时涉及 ERP（旺店通）与多个电商开放平台（抖店、拼多多）。接口路径与错误码要求精确词项匹配，现场故障描述又多为口语化表达；更重要的是，**同一接口在不同客户端版本下适用结论可能完全相反**（如 `trade_push.php` 在客户端 V2.4.4 及以下不支持，V2.4.5.0 起支持），纯向量相似度检索极易跨平台串台或返回错误版本的文档。
- **核心检索架构**：父子分块（子块 300 字精准定位字段与错误码、父块 1200 字保留前置条件与限制）+ BGE-M3 稠密与稀疏双路召回 + Milvus 表达式预筛与 `WeightedRanker` 混合融合 + 版本区间语义过滤 + BGE-Reranker 交叉编码重排 + 缺关键现场信息前置追问。
- **可证伪评估闭环**：针对初期规则评估漏检“越界引用 `[9]`”与“关键词命中但结论写反”的缺陷，重构 `v2` 结构化评估口径（18 题基准集：文档命中 13/13、引用合法 13/13、版本筛选 6/6、缺信息追问 3/3、资料不足拒答 2/2），并包含 12 题检索消融对照实验（稠密 vs 混合 vs 混合+重排）。

> **项目性质与数据边界说明**：本项目为个人工程实践项目，非企业线上生产系统。知识库基于旺店通开放平台、抖音电商开放平台、拼多多开放平台的公开 API 文档、帮助文档与本人整理的版本对照说明构建，未使用任何未授权的企业内部资料或真实客户业务数据。

## 1. 资料范围与授权边界

公开资料统一带结构化 `【文档元数据】` 头，记录标题、章节、产品、平台、适用版本、文档类型、原文链接、更新时间和授权状态。

| 目录 | 数量 | 内容 |
| --- | --- | --- |
| `rag_qa/data/product_docs/` | 6 | 旺店通创建原始订单、销售出库单查询、库存同步查询、库存同步回写、公共错误码、电子面单号查询 |
| `rag_qa/data/platform_docs/` | 4 | 抖店订单列表、抖店电子面单、拼多多订单同步、拼多多电子面单 |
| `rag_qa/data/release_notes/` | 3 | 旺店通接口适用版本对照、低版本接口限制、网页版库存查询 |
| `rag_qa/data/internal_docs/` | 0 | 企业私有故障复盘、升级规则与客户资料目录；未获授权默认留空不导入 |

当前建库后共生成 **52 个父/子块**，Milvus 集合名 `warehouse_saas_kb_qa`。

资料使用边界：
- 回答中强制标注适用平台、产品和原文链接，严禁将抖店接口字段或错误码套用至拼多多或旺店通；
- 正文区分三类来源：厂商官方原文摘录、`release_notes/` 中 2 份标题带“（整理）”的版本对照笔记，以及基于官方文档归纳的“排查顺序建议”；
- 本轮已对 `trade_push.php` 与开放平台公共错误码页做在线核对，其余原文链接沿用整理时记录，厂商改版时需重新核验。

## 2. 一次问答的完整链路

1. **领域初判与追问拦截（`triage.py`）**：先识别问题归属（订单 / 库存 / 面单），检查是否缺失决定排查分支的现场要素（平台、错误码、完整版本号、异常阶段）。缺失时直接返回追问，不进入 FAQ 或向量检索。
2. **FAQ 分流**：高频固定问法走 FAQ BM25（MySQL 存储，不可用时自动回退本地 CSV）；含错误码、版本号、多业务对象或需现场判断的问题跳过 FAQ 进入主检索链路。
3. **指代与问题改写**：跟进追问结合上一轮问题补全检索词；切换业务范围或无关历史不强行拼接。
4. **双路混合召回**：BGE-M3 一次推理同时产出 1024 维稠密向量与稀疏词权重，从 Milvus 召回候选子块。
5. **父块回溯与去重**：命中子块后映射回完整父块并按 `parent_id` 去重，避免子块切片丢失版本前提与接口限制。
6. **多维元数据筛选**：产品、平台在召回阶段下推为 Milvus 标量过滤表达式；适用版本在父块去重后、重排前执行语义区间判定。
7. **交叉编码重排与双阈值拦截**：BGE-Reranker 对候选父块重排，低于 `min_score = 0.2` 丢弃；最高分低于 `MIN_ANSWER_SCORE = 0.35` 时走“资料不足”出口，不强行生成。
8. **受控生成与引用清洗**：按“适用条件 → 排查顺序 → 来源”结构化生成，清理超出当次候选编号范围的 `[n]` 引用。

## 3. 核心检索、版本过滤与引用实现细节

### 3.1 稠密、稀疏与两种融合路径
- **Milvus 服务端原生路径（默认实测路径）**：使用 `hybrid_search` + `WeightedRanker` 加权融合（`dense_weight = 0.7`，`sparse_weight = 1.0`），评估 JSON 中记录为 `hybrid_mode = native`。
- **Milvus Lite 回退路径**：无独立服务端时分别执行稠密与稀疏召回，在客户端以 RRF（`k = 60`）融合。两条路径融合机制不同，日志与评估报告如实区分记录。

### 3.2 版本区间语义判断与后置过滤取舍
- 版本号统一补零对齐至 4 段（`V2.4.5` 与 `V2.4.5.0` 等价），支持判定「`V2.4.5.0 及以上`」「`V2.4.4 及以下`」「`全版本`」「`多版本对照`」「`网页版`」「`平台最新`」。
- 区分**完全覆盖 / 部分重叠 / 不适用 / 仅供对照**四类关系：仅部分覆盖时向提示词注入“版本适用范围提示”要求写明附加条件；全部候选仅部分覆盖时先追问完整版本号；“多版本对照”不混入单版本直接适用结论。
- 启用版本筛选时，Milvus 初始召回池自动扩大至 **3 倍（上限 200）** 以缓解后置过滤漏召回；但若极端情况下前排全被其他版本占据，仍可能过滤为空（属召回/过滤阶段边界，未做按版本分桶预索引）。

### 3.3 引用校验边界
- 代码确保正文中出现的 `[n]` 全部对应本轮真实返回的父块编号，并展示标题、章节、产品、平台、版本与原文 URL；
- 不做句子级 NLI 事实蕴含核验，不能将“引用编号合法”等同于“完全消除模型推理幻觉”。

## 4. 环境准备与快速启动

### 4.1 依赖环境
- Python 3.10+（实测环境 3.12）
- 本地模型权重：`BAAI/bge-m3`（置于 `rag_qa/models/bge-m3`）、`BAAI/bge-reranker-large`（置于 `rag_qa/models/bge-reranker-large`）
- Milvus 2.4+ 服务端（默认 `localhost:19530`，库 `enterprise_knowledge`；无服务端可配 `QA_MILVUS_URI` 走 Milvus Lite）
- OpenAI 兼容大模型接口：默认配置 DeepSeek，通过环境变量 `DEEPSEEK_API_KEY` 注入密钥
- 可选组件：MySQL（`warehouse_faq.faq`，不可用自动回退 `mysql_qa/db/faq_knowledge_base.csv`）与 Redis

### 4.2 建库、启动与健康检查

```powershell
# 1. 复制配置模板并按本机修改端口与模型路径
copy base/config.example.ini base/config.ini

# 2. 文档解析、父子切分与向量入库
python -m rag_qa.main --data-processing

# 3. 启动 Web 与 WebSocket 流式服务（默认 http://127.0.0.1:8081）
python app.py
```

验证服务状态：
```powershell
curl.exe http://127.0.0.1:8081/health
curl.exe http://127.0.0.1:8081/api/filters
```

### 4.3 可选模式：企业私有资料隔离检索与消融实验
项目额外支持独立的企业私有知识库隔离模式（独立 Milvus 集合 `warehouse_private_kb` + 本地 Ollama `qwen2.5:7b` + `QA_ACCESS_TOKEN` 访问鉴权，不调用外部公网模型）：

```powershell
$env:QA_PRIVATE_MODE = '1'
$env:QA_ACCESS_TOKEN = (New-Guid).Guid
python -m rag_qa.main --demo-private-data
python app.py
```

运行 12 题检索消融对照实验（对比纯稠密检索、混合检索、混合检索 + Reranker 重排在易混淆文档对上的 `hit@1` / `hit@3` 与耗时）：
```powershell
python -m rag_qa.rag_assessment.private_retrieval
```

### 5.2 18 题评估结果与 `v1 → v2` 口径演进

题目定义见 [`warehouse_evaluate_data.json`](rag_qa/rag_assessment/warehouse_evaluate_data.json)（13 道有依据检索题、3 道缺信息追问题、2 道资料不足题）。新口径实测结果见 [`warehouse_evaluate_results_v2.json`](rag_qa/rag_assessment/warehouse_evaluate_results_v2.json)：

| 评估维度 | 实测结果 | 统计分母与判定规则 |
| --- | --- | --- |
| 总体通过 | 18/18 | 全部 18 道回归样本 |
| 预期文档命中 | 13/13 | 13 道有依据题；空标题直接排除 |
| 引用编号合法 | 13/13（越界 0） | 至少含一个 `[n]` 且全部在当次返回来源编号内 |
| 版本筛选准确 | 6/6（含 partial 1） | 6 道带版本条件题；严禁混入不适用或仅供对照文档 |
| 关键结论方向判定 | 8/8 通过，0 相反，5 待人工复核 | 8 道具二元明确结论题自动判别正误；开放式排查题标为人工复核，不冒充自动通过 |
| 缺信息追问 / 资料不足 | 3/3 与 2/2 | 检验检索前追问拦截与无依据拒答 |

- **为什么废弃旧版 `v1` 口径**：旧口径仅检查“标题命中 + 关键词覆盖 ≥ 50% + 含 `[n]`”，既无法拦截越界编号 `[9]`，也无法拦截“关键词全中但把‘不支持’写成‘支持’”的相反结论。该组反例已固化至 [`tests/test_warehouse_eval_guards.py`](tests/test_warehouse_eval_guards.py)。
- **真实缺陷定位与修复记录**：首轮评估中 E06（库存回写后果）与 E08（面单接入准备）曾出现 0 召回，根因定位为 `triage.py` 中泛化词“同步”抢占了库存域优先级、且将知识咨询误判为现场报障追问；修正具体业务对象优先级并放行“后果/区别/准备/流程”类问法后回归通过。

## 7. 已知限制

- 公开资料仅覆盖旺店通、抖店、拼多多三方；淘宝、京东、快手等平台问题均按资料不足拒答。
- 版本筛选在父块去重后执行，极端候选分布下仍存在后置过滤漏召回风险。
- 18 题评估属于小规模规则回归（其中 5 道开放排查题结论仍需人工复核），不能代表真实线上工单分布或“100% 生产准确率”。
- 默认公开演示为单工作空间设计，不包含多租户 RBAC 与工单状态机流转。
