# MySQL 学科知识手册

## 1. 存储引擎 InnoDB 与 MyISAM

MySQL 采用插件式存储引擎，同一库中不同表可以使用不同引擎。InnoDB 是 5.5 之后的默认引擎，支持事务、行级锁、外键、崩溃恢复，采用聚簇索引组织数据。

MyISAM 不支持事务与行锁，只支持表锁，索引与数据分离，读取速度快但写入并发差，崩溃后容易损坏。MyISAM 在只读或数据仓库场景仍有使用，但新项目一般不选。

选择建议：除明确的只读分析场景外，一律用 InnoDB。需要全文检索可以用 InnoDB 的全文索引或引入 Elasticsearch。

## 2. 索引与 B+ 树

索引是帮助快速定位数据的数据结构。MySQL 的 InnoDB 使用 B+ 树，原因是它适合磁盘存储：树高低、节点大，一次 I/O 能读取大量键值，通常三层就能支撑千万级数据。

B+ 树与 B 树的区别：B+ 树只有叶子节点存数据，非叶子节点只存索引键，因此单节点能容纳更多键，树更矮；叶子节点之间用双向链表连接，天然支持范围查询与排序。

一次查询的 I/O 次数约等于树高。这也是为什么索引列要尽量短：键越短，单节点容纳的键越多，树越矮。

## 3. 聚簇索引与二级索引

InnoDB 的聚簇索引以主键组织数据，叶子节点直接存放整行记录，因此一张表只能有一个聚簇索引。如果没有显式主键，InnoDB 会选唯一非空索引，否则生成隐藏的 row_id。

二级索引的叶子节点存放的是索引列加主键值，不是行数据。通过二级索引查询非索引列时需要"回表"：先查到主键，再用主键查聚簇索引。

回表是性能损耗的主要来源。覆盖索引可以避免回表：如果查询涉及的列都在索引中，直接从索引返回即可。因此 `select *` 往往比只查必要列更慢。

## 4. 事务与 ACID

事务是一组要么全部成功要么全部失败的操作。ACID 分别指原子性、一致性、隔离性、持久性。

原子性由 undo log 保证：修改前的旧值被记录，回滚时反向执行。持久性由 redo log 保证：修改先写日志再刷盘，崩溃后可按日志重放。隔离性由锁与 MVCC 保证。一致性是最终目标，由前三者与应用层约束共同保证。

redo log 是物理日志，记录页的修改，循环写；undo log 是逻辑日志，记录反向操作，用于回滚与 MVCC 的历史版本。

## 5. 隔离级别与 MVCC

SQL 标准定义四个隔离级别：读未提交、读已提交、可重复读、串行化。MySQL 默认是可重复读。

各级别对应的问题：读未提交会脏读；读已提交避免脏读但有不可重复读；可重复读避免不可重复读但理论上仍有幻读；串行化全部避免但并发最低。

MVCC 通过版本链与 ReadView 实现：每行记录有隐藏的事务 ID 与回滚指针，串成版本链；查询时根据 ReadView 判断哪个版本对当前事务可见。读已提交在每次查询时生成新 ReadView，可重复读在事务开始时生成一次，因此后者能保证同一事务内多次读取结果一致。

InnoDB 在可重复读下用间隙锁（Next-Key Lock）解决了大部分幻读问题。

## 6. 锁机制

按粒度分为表锁、行锁、间隙锁。按模式分为共享锁（S）与排他锁（X）。InnoDB 的行锁是加在索引上的，如果查询没有走索引，会退化为锁全表。

意向锁是表级锁，用来说明表中存在行锁，避免加表锁时逐行检查。插入意向锁用于标记将要插入的位置。

死锁是两个事务互相持有对方需要的锁。InnoDB 有死锁检测，会回滚代价较小的事务。避免死锁的方法：按固定顺序访问资源、缩短事务、减少锁范围、为条件列建索引。

## 7. 慢查询与执行计划

开启慢查询日志（slow_query_log）并设置 long_query_time，可以捕获执行时间超阈值的 SQL。用 mysqldumpslow 或 pt-query-digest 做聚合分析，找出 Top SQL。

`explain` 查看执行计划，重点字段：type 表示访问类型，从好到差为 system、const、eq_ref、ref、range、index、ALL；key 表示实际使用的索引；rows 表示预估扫描行数；Extra 中出现 Using filesort 或 Using temporary 通常意味着需要优化。

`explain analyze`（8.0.18 之后）能给出实际执行耗时，比仅看预估更准确。优化方向通常是：加合适索引、改写 SQL 避免索引失效、减少回表、拆分大查询。

## 8. 索引失效的常见场景

对索引列做函数运算或表达式计算会导致失效，例如 `where date(create_time) = '2026-01-01'`，应改为范围查询。

隐式类型转换会失效：字符串列用数字比较，MySQL 会把列转成数字，索引失效。例如手机号存为 varchar 却写 `where phone = 13800000000`。

前导模糊匹配 `like '%abc'` 无法使用索引，`like 'abc%'` 可以。使用 or 且其中一列无索引会退化为全表扫描。复合索引不满足最左前缀原则也会失效。

使用 `!=`、`not in`、`is not null` 时优化器可能放弃索引，取决于数据分布与选择性。

## 9. 主从复制

主从复制流程：主库把变更写入 binlog；从库的 IO 线程连接主库拉取 binlog 写入 relay log；从库的 SQL 线程重放 relay log，使数据与主库一致。

binlog 格式有三种：statement 记录 SQL 语句，日志小但某些函数结果不确定；row 记录行的前后镜像，最安全但日志大；mixed 由 MySQL 自动选择。

主从延迟的常见原因：从库配置差、大事务、无主键导致逐行更新慢、从库承担大量查询。解决方向包括开启并行复制、拆分大事务、提升从库配置、关键读走主库。

半同步复制要求至少一个从库确认收到日志后主库才返回，能在一定程度上减少数据丢失。

## 10. 分库分表

单表数据量过大时，索引变高、DDL 变慢、备份恢复困难。常见阈值是单表千万行或单库磁盘接近上限，具体要看行宽与访问模式。

垂直拆分按业务或按列拆：把不常用的大字段拆到扩展表，把不同业务拆到不同库。水平拆分按行拆：按用户 ID 取模、按时间范围分片。

分片带来新问题：跨库 join 与跨库事务、全局唯一 ID、分页排序、扩容迁移。常用方案是引入中间件（ShardingSphere）、用雪花算法生成 ID、避免跨片 join 或在应用层聚合。

分库分表是最后手段，优先考虑索引优化、读写分离、归档冷数据。

## 11. 日志体系

redo log 属于 InnoDB，记录物理页修改，保证崩溃恢复与持久性，循环写，大小固定。undo log 记录反向操作，用于回滚与 MVCC，存放在 undo 表空间。

binlog 属于 Server 层，记录所有修改数据的语句或行变更，用于主从复制与数据恢复，追加写。relay log 是从库特有的中继日志。

错误日志记录启动、运行、崩溃信息，是排查问题的第一手资料。慢查询日志记录超阈值 SQL。通用日志记录所有请求，开销大，一般只在排查时临时开启。

两阶段提交保证 redo log 与 binlog 一致：先写 redo 并置为 prepare，再写 binlog，最后提交 redo 为 commit。

## 12. 常见优化手段

SQL 层面：只查需要的列、避免 `select *`、用 limit 限制结果集、用 join 替代子查询（视情况）、批量插入替代循环单条插入、避免在循环中查库。

索引层面：为 where、order by、group by 的列建索引，使用复合索引并遵循最左前缀，用覆盖索引减少回表，定期清理冗余索引。

架构层面：读写分离、加缓存（注意一致性）、分区表、归档历史数据、必要时分库分表。

配置层面：合理设置 innodb_buffer_pool_size（通常为物理内存的 50% 到 70%）、连接数、日志刷盘策略。
