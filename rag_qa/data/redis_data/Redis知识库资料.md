## 1. Redis 的基本概念与使用场景

### 1.1 概念

Redis 是基于内存的键值数据库，支持字符串、哈希、列表、集合、有序集合等多种数据结构，并提供持久化、过期、发布订阅、事务、Lua 脚本和集群等能力。它常被用作缓存，但也能承担计数器、会话存储、排行榜、限流、消息流等角色。

Redis 的键是二进制安全的字符串，值可以是不同数据结构。数据主要放在内存中，因此访问延迟通常较低；但内存容量有限，持久化和故障恢复也需要设计，不能把“在内存中”理解为“不会丢数据”。

### 1.2 原理或使用方法

Redis 常用单线程事件循环处理命令，因此单条命令通常原子执行，多个客户端命令仍可能交错。Redis 6 起网络 I/O 可使用多线程，但命令执行模型不能简单理解为“所有环节都完全单线程”。Lua 脚本可把多个操作组合为一个原子执行单元，但脚本过长会阻塞其他请求。

选择 Redis 场景时应问三个问题：数据是否允许丢失或可重建？访问模式是否主要是键值或少量结构化操作？内存成本和一致性要求是否可接受？不适合把 Redis 当作唯一的关系数据存储来处理复杂事务查询。

### 1.3 示例

```bash
redis-cli SET user:1:name "小林"
redis-cli SET page:home:views 0
redis-cli INCR page:home:views
redis-cli GET page:home:views
redis-cli EXPIRE page:home:views 60
redis-cli TTL page:home:views
```

这组命令分别演示字符串写入、计数递增、过期设置和剩余时间查询。计数适合用 `INCR` 原子增加，不必先 `GET` 再 `SET`。

### 1.4 易错点和注意事项

- Redis 不是“绝对不丢数据”的存储。持久化策略、复制延迟和故障切换都可能影响数据安全。
- 不要把大量业务数据无上限地放入内存，必须设置容量、淘汰策略和监控。
- 单条命令原子不代表多条命令组成的事务自动一致；需要原子组合时应使用 Lua、事务或重新设计数据模型。
- Redis 适合简单键访问和高频操作，不适合替代需要复杂连接、约束和多表事务的关系数据库。

### 1.5 常见问题

**问：Redis 为什么快？**  
答：数据主要在内存中，数据结构针对常见操作优化，事件循环减少线程切换；但网络往返、慢命令、持久化和大键仍会造成延迟。

**问：Redis 可以做数据库吗？**  
答：可以存储部分业务数据，但要根据持久性、容量、查询能力和一致性要求判断。很多系统把 Redis 作为缓存或辅助存储，而不是唯一数据源。

**问：Redis 单线程会不会成为瓶颈？**  
答：命令执行通常是单线程的，慢命令会阻塞其他请求；但网络 I/O、后台持久化和集群分片等机制可分担部分工作，实际瓶颈需通过监控和压测判断。

## 2. String、Hash、List、Set、Sorted Set

### 2.1 概念

String 是最基本的二进制安全字符串，可保存文本、序列化数据或整数计数。Hash 保存字段到值的映射，适合表示一个对象的多个属性。List 是有序的字符串列表，支持两端插入删除。Set 是无序不重复集合。Sorted Set（ZSet）为每个成员关联分数，并按分数排序，适合排行榜和范围查询。

这些结构不是 Java 或 Python 集合的完全复制品。例如 Redis List 是链表式结构，按索引访问中间元素可能较慢；ZSet 的排序依赖分数，分数相同再按成员字典序排列。

### 2.2 原理或使用方法

String 常用 `SET/GET/INCR`；Hash 用 `HSET/HGET/HGETALL`；List 用 `LPUSH/RPUSH/LPOP/RPOP/LRANGE`；Set 用 `SADD/SMEMBERS/SINTER`；ZSet 用 `ZADD/ZRANGE/ZREVRANGE/ZINCRBY`。

选择结构应围绕访问模式：需要按字段读取对象属性可用 Hash，但字段很多时 `HGETALL` 可能产生大响应；需要去重和集合运算用 Set；需要按分数排序用 ZSet。大键和高频全量读取是常见性能风险。

### 2.3 示例

```bash
# Hash：保存用户资料
redis-cli HSET user:1 name "小林" score 90 city "北京"
redis-cli HGET user:1 name
redis-cli HINCRBY user:1 score 5

# List：消息队列式的两端操作
redis-cli RPUSH queue:jobs job-1 job-2
redis-cli LPOP queue:jobs

# Set：标签去重与交集
redis-cli SADD article:1:tags redis cache
redis-cli SADD article:2:tags redis database
redis-cli SINTER article:1:tags article:2:tags

# ZSet：排行榜
redis-cli ZADD leaderboard 90 "小林" 85 "小周"
redis-cli ZREVRANGE leaderboard 0 9 WITHSCORES
```

`HINCRBY` 适合对 Hash 中的数值字段原子增加。`ZREVRANGE 0 9 WITHSCORES` 按分数从高到低取前十名并返回分数。

### 2.4 易错点和注意事项

- `HGETALL` 会一次返回整个 Hash，字段很多时可能阻塞客户端或占用大量网络带宽；可改用 `HSCAN` 分批读取。
- Set 和 ZSet 的成员必须能作为字符串保存。复杂对象应先序列化，并明确版本和兼容策略。
- List 不是天然可靠消息队列。需要消费确认、消费者组和消息重投时，应使用 Redis Streams 或专门消息系统。
- Sorted Set 的分数是浮点数，相等分数按成员排序；不要依赖浮点分数表达精确金额。

### 2.5 常见问题

**问：Hash 和 String 存 JSON 怎么选？**  
答：需要频繁读写单个字段、原子增减字段时 Hash 更方便；整体读写、结构复杂或需要保留嵌套 JSON 时可用 String，但要接受全量序列化成本。

**问：List 能实现栈和队列吗？**  
答：可以。`LPUSH` 配 `LPOP` 类似栈，`RPUSH` 配 `LPOP` 类似队列；但可靠性、消费确认和并发消费语义需另行设计。

**问：ZSet 如何实现排行榜？**  
答：用成员表示用户、分数表示排名依据，`ZADD` 更新分数，`ZREVRANGE` 取前 N 名。分数更新频繁时要关注写入量和内存。

## 3. 常见命令、键设计与过期时间

### 3.1 概念

Redis 键通常采用冒号分隔的命名空间，如 `user:1:profile`，便于阅读和按前缀管理。键必须唯一，设计时应包含业务域、对象类型和 ID，避免使用无意义或过长的键。

过期时间让键在指定时间后自动删除，常用于缓存和短期会话。`EXPIRE` 设置秒级过期，`PEXPIRE` 使用毫秒，`TTL/PTTL` 查询剩余时间，`PERSIST` 移除过期时间。Redis 还支持 `SET key value EX seconds` 在写入时同时设置过期。

### 3.2 原理或使用方法

Redis 通过惰性删除和定期主动抽样清理过期键。键到期不等于立即从内存消失；访问时会检查过期，后台也会周期性清理。因此不能把 `TTL` 当作精确的定时任务调度器。

过期与内存淘汰是不同概念：过期由键的 TTL 触发，淘汰是在 `maxmemory` 达到上限时按策略移除键。即使没有设置过期，内存压力也可能触发淘汰；反之，即使设置过期，在未达到内存限制前也可能暂时保留已过期但尚未清理的键。

### 3.3 示例

```bash
# 推荐：写入时原子设置值和过期时间
redis-cli SET session:abc "user-1" EX 1800 NX

# 查看和移除过期时间
redis-cli TTL session:abc
redis-cli PERSIST session:abc

# 使用 SCAN 渐进遍历，不要在生产环境直接用 KEYS *
redis-cli SCAN 0 MATCH "user:*" COUNT 100
```

`SET ... EX 1800 NX` 表示仅当键不存在时写入，并设置 30 分钟过期。`SCAN` 返回游标和一批键，应该循环直到游标为 0，不能保证一次返回全部数据。

### 3.4 易错点和注意事项

- 不要在生产环境使用 `KEYS *` 遍历大量键，它可能长时间阻塞命令执行；应使用 `SCAN`。
- `EXPIRE` 的时间单位容易混淆，秒和毫秒要分清；批量设置过期可考虑 `PIPELINE` 降低往返次数。
- 给缓存键设置过期时加入随机抖动，可减少同一时刻大量键同时失效的风险。
- 键名过长会增加内存占用；键名过短又会降低可读性，应根据团队规范平衡。

### 3.5 常见问题

**问：过期键会立刻释放内存吗？**  
答：不一定。Redis 采用惰性删除和定期清理，键到期后可能仍暂时占用内存，直到被访问或后台清理。

**问：`TTL` 返回 -1 和 -2 分别表示什么？**  
答：通常 `-1` 表示键存在但没有设置过期时间，`-2` 表示键不存在。应以实际版本文档为准。

**问：为什么不要用 `KEYS` 找键？**  
答：它会扫描整个键空间且可能阻塞其他命令。`SCAN` 是渐进式遍历，适合生产环境分批处理。

## 4. 缓存穿透、缓存击穿与缓存雪崩

### 4.1 概念

缓存穿透是查询的数据在缓存和数据库中都不存在，每次请求都绕过缓存访问数据库。缓存击穿是某个热点键过期或被删除的瞬间，大量并发请求同时回源数据库。缓存雪崩是大量键在同一时间段失效，或缓存服务整体不可用，导致数据库承受突发流量。

三者的区别在于问题对象：穿透是“永远查不到的数据”，击穿是“单个热点键失效”，雪崩是“大面积失效或整体故障”。

### 4.2 原理或使用方法

穿透可缓存空结果并设置较短过期时间，或在入口做参数校验、限流；布隆过滤器可提前判断“可能存在/一定不存在”，但有误判和删除困难，不能替代数据库校验。击穿可用互斥重建、单飞请求合并、逻辑过期或热点永不过期配合后台更新。雪崩可给过期时间加随机抖动、部署高可用缓存、设置降级和限流。

任何方案都要考虑一致性：缓存空值可能掩盖后来新增的数据；逻辑过期需要处理旧值读取和异步刷新失败。

### 4.3 示例

```bash
# 缓存空结果，过期时间较短，避免持续穿透
redis-cli SET product:404:cache "__NULL__" EX 60 NX

# 热点键重建锁，只有获得锁的请求回源
redis-cli SET lock:product:1001:rebuild "worker-1" NX PX 5000

# 给普通缓存过期时间加随机抖动（示例示意，不是原子命令）
redis-cli SET product:1001 "{...}" EX 1837
```

第一段用特殊标记表示“确认不存在”，应用读取时要区分真实值和空结果标记。重建锁必须设置过期时间，并在完成后释放；释放时要校验持有者，避免误删其他请求的锁。

### 4.4 易错点和注意事项

- 缓存空值需要短 TTL 和明确标记，否则新增数据后仍会读到旧的“空结果”。
- 互斥重建会引入等待和锁竞争，应设置超时与降级，不能让所有请求无限等待。
- 雪崩方案不能只靠随机 TTL，还要考虑 Redis 整体不可用、网络分区和数据库容量。
- 布隆过滤器只能减少明显不存在的查询，不能保证所有“可能存在”的键都真实存在。

### 4.5 常见问题

**问：缓存穿透和缓存击穿最容易混淆的地方是什么？**  
答：穿透的数据在数据库中也不存在；击穿的数据真实存在，只是热点缓存失效导致并发回源。

**问：热点键设置为永不过期是否安全？**  
答：可以减少失效瞬间的并发回源，但必须设计后台更新、版本切换和内存管理，否则可能长期返回旧数据。

**问：缓存雪崩只发生在过期时间吗？**  
答：不只。缓存节点故障、网络异常、集中发布导致 key 前缀变化，也可能造成大面积未命中。

## 5. 缓存与数据库一致性

### 5.1 概念

缓存与数据库一致性指缓存中的数据是否与数据库最新已提交状态相符。常见模式是 Cache Aside：读请求先查缓存，未命中查数据库并回填；写请求更新数据库后删除缓存，而不是直接更新缓存。

强一致通常需要分布式事务、版本控制或让数据库成为唯一事实来源；普通缓存方案多数追求最终一致，并接受短暂旧值。必须明确业务能容忍多长的旧数据窗口。

### 5.2 原理或使用方法

Cache Aside 的典型顺序是：更新数据库成功后删除缓存。若先删缓存再更新数据库，并发读可能在数据库更新前把旧值重新写回缓存；若先更新数据库再删缓存，仍可能出现删除失败、并发读写交错等问题。

降低不一致的常见手段包括：给缓存设置 TTL、延迟双删、版本号或逻辑过期、通过 binlog/CDC 异步失效缓存。延迟双删不是严格证明的强一致方案，只是降低特定竞态窗口；可靠性要求高时应使用可重试的失效消息和版本校验。

### 5.3 示例

```python
# 伪代码：Cache Aside 读取流程；redis_client 与 db 为示意对象
def get_user(user_id):
    key = f"user:{user_id}"
    cached = redis_client.get(key)
    if cached is not None:
        return deserialize(cached)

    user = db.query_one("SELECT id, name FROM users WHERE id = %s", user_id)
    if user is None:
        redis_client.set(key, "__NULL__", ex=60)
        return None

    redis_client.set(key, serialize(user), ex=300)
    return user


def update_user(user_id, name):
    db.execute("UPDATE users SET name = %s WHERE id = %s", name, user_id)
    db.commit()
    redis_client.delete(f"user:{user_id}")  # 数据库成功后失效缓存
```

示例只展示顺序，未处理删除失败、并发回填和事务边界。生产中应把缓存失效纳入重试机制，并监控数据库提交与缓存删除之间的异常。

### 5.4 易错点和注意事项

- 写数据库成功但删除缓存失败时，旧缓存可能保留到 TTL 到期；应有重试和补偿。
- 读请求回填缓存前若数据库刚被更新，可能把较旧值写回；版本号和逻辑过期可帮助识别。
- 不要用“先更新缓存再更新数据库”作为默认方案，缓存更新失败会造成更难处理的不一致。
- 多级缓存（本地缓存 + Redis）会扩大一致性窗口，需要广播失效或版本机制。

### 5.5 常见问题

**问：为什么通常删除缓存而不是更新缓存？**  
答：删除后下次读取从数据库重建，逻辑简单；并发更新缓存容易产生覆盖顺序问题，且可能写入无人读取的值。

**问：延迟双删能保证强一致吗？**  
答：不能。它只能降低特定竞态概率，仍受延迟估计、执行失败和并发写影响。强一致需要更完整的协议或放弃缓存作为权威数据源。

**问：缓存和数据库最终一致可以接受吗？**  
答：取决于业务。商品展示短暂旧值可能可接受，余额、库存扣减等关键数据不能只依赖普通缓存失效策略。

## 6. RDB 与 AOF 持久化

### 6.1 概念

RDB 把某一时刻的数据快照写入磁盘，文件紧凑、恢复通常较快，但两次快照之间的数据可能丢失。AOF 追加记录写命令，可按不同同步策略把数据写入磁盘，通常提供更高持久性，但文件更大、恢复和重写有额外开销。

Redis 4 起可使用 RDB-AOF 混合持久化；Redis 7 的 AOF 实现有版本变化。具体配置项和行为应以部署版本为准，不能把旧版本文档直接套到新版。

### 6.2 原理或使用方法

`BGSAVE` 通过 fork 子进程生成 RDB，利用写时复制减少主进程阻塞，但 fork 本身和内存页复制仍可能带来延迟，数据量和内存越大越明显。`SAVE` 会阻塞主线程，通常不适合生产环境主动执行。

AOF 的 `appendfsync` 常见取值包括 `always`、`everysec`、`no`。`always` 持久性更强但每次写入同步成本高；`everysec` 在性能与丢失窗口间折中；`no` 交给操作系统决定，故障时丢失风险更高。AOF 重写压缩冗余命令，重写期间也需考虑内存和 I/O。

### 6.3 示例

```bash
# 查看持久化相关配置
redis-cli CONFIG GET save
redis-cli CONFIG GET appendonly
redis-cli CONFIG GET appendfsync

# 后台生成 RDB 快照（示例；生产操作需评估 fork 和磁盘压力）
redis-cli BGSAVE

# 查看最近一次保存状态
redis-cli INFO persistence
```

不要直接把 `CONFIG SET appendonly yes` 当成无成本热切换。开启 AOF 可能触发重写和磁盘 I/O，应在测试环境验证版本行为和资源余量。

### 6.4 易错点和注意事项

- RDB 不是实时备份，故障时可能丢失最近一次快照后的写入。
- AOF `everysec` 也不是零丢失承诺；操作系统缓存、磁盘故障和主从切换都可能影响结果。
- fork 时内存占用可能短时上升，容器环境要预留内存并避免触发 OOM。
- 持久化文件写入失败、磁盘满或权限错误会影响恢复能力，应监控 `INFO persistence` 的相关指标。

### 6.5 常见问题

**问：RDB 和 AOF 应该选哪个？**  
答：需要快速备份和恢复可用 RDB；需要更细粒度持久性可用 AOF；很多部署会组合使用。选择取决于可接受的数据丢失窗口和运维成本。

**问：AOF 文件越来越大怎么办？**  
答：可执行 AOF 重写，用当前数据状态生成更紧凑的命令集合。重写需要额外 CPU、内存和磁盘，应安排合适时机。

**问：持久化开启后还会丢数据吗？**  
答：会。持久化降低风险但不等于零丢失，尤其在异步复制、故障切换和磁盘故障场景。

## 7. 内存淘汰策略

### 7.1 概念

当 Redis 使用内存达到 `maxmemory` 上限时，淘汰策略决定移除哪些键。常见策略包括 `noeviction`、`allkeys-lru`、`volatile-lru`、`allkeys-lfu`、`volatile-lfu`、`allkeys-random`、`volatile-random` 和 `volatile-ttl`。

LRU 关注最近使用时间，LFU 关注访问频率；随机策略不看使用模式；`volatile-*` 只从设置了过期时间的键中选择，`allkeys-*` 从所有键中选择。`noeviction` 在内存不足时让写入失败，适合不能随意丢数据的场景。

### 7.2 原理或使用方法

Redis 的 LRU 通常是近似实现，通过采样选择候选而非维护精确全局顺序，因此不能把淘汰结果当成严格最近最少使用。LFU 也需要配置和计数器衰减，适合长期热点但会受到访问模式变化影响。

选择策略前先区分 Redis 中的数据：可重建缓存可使用 `allkeys-lru` 或 `allkeys-lfu`；不能丢失的会话或队列数据不应与缓存混在同一实例中随意淘汰。更稳妥的做法是按业务隔离实例或键空间。

### 7.3 示例

```bash
redis-cli CONFIG GET maxmemory
redis-cli CONFIG GET maxmemory-policy

# 示例：将纯缓存实例配置为 allkeys-lfu（需结合版本与运维流程）
redis-cli CONFIG SET maxmemory-policy allkeys-lfu

# 查看键的内存占用
redis-cli MEMORY USAGE user:1
redis-cli INFO memory
```

生产环境修改淘汰策略应通过配置管理和变更流程执行，不能只在单节点临时 `CONFIG SET` 后忘记持久化。

### 7.4 易错点和注意事项

- 淘汰并不等于过期。没有设置 TTL 的键也可能被 `allkeys-*` 策略移除。
- 把不可丢失数据和缓存放在同一实例并启用 `allkeys-*`，可能直接淘汰关键数据。
- `maxmemory` 需要为 fork、复制缓冲区和客户端输出缓冲区预留空间，不能把容器内存全部分配给数据。
- 淘汰会增加延迟和数据库回源压力，应同时监控命中率、驱逐数量和内存曲线。

### 7.5 常见问题

**问：`volatile-lru` 会淘汰没有过期时间的键吗？**  
答：通常不会。它只在设置了过期时间的键中选择；若可淘汰键不足，写入可能失败。

**问：LRU 和 LFU 有什么区别？**  
答：LRU 偏向保留最近访问的键，LFU 偏向保留访问频率高的键。短时热点和长期热点适合的策略可能不同。

**问：缓存命中率下降一定是内存不足吗？**  
答：不一定。键过期、业务访问变化、发布导致键名改变或缓存节点故障都可能造成下降，应结合指标排查。

## 8. 主从复制、哨兵与集群

### 8.1 概念

主从复制让一个主节点把写命令传播给一个或多个从节点，从节点可承担读请求和故障备份。哨兵（Sentinel）监控主从节点，在主节点故障时进行选主和切换。Redis Cluster 通过哈希槽把键分布到多个主节点，支持水平扩展和分片。

复制默认是异步的，主节点确认写入不代表从节点已经收到。故障切换可能丢失尚未复制的数据，因此 Redis 复制不能等同于强一致共识系统。

### 8.2 原理或使用方法

从节点通过 `REPLICAOF` 建立复制，初次同步可能进行全量传输，之后增量传播。网络中断后可尝试部分重同步，但是否成功取决于复制积压缓冲区和偏移量。

Sentinel 需要多个实例共同判断故障，客户端通过 Sentinel 获取当前主节点。Cluster 将键空间分为 16384 个槽，每个主节点负责一部分槽；客户端收到 `MOVED` 后更新路由，`ASK` 表示临时重定向。多键操作通常要求键在同一槽，可使用 hash tag 控制。

### 8.3 示例

```bash
# 查看复制角色和状态
redis-cli INFO replication

# 在从节点上查看复制偏移量
redis-cli INFO replication | grep master_repl_offset

# 查看集群节点与槽分配
redis-cli CLUSTER INFO
redis-cli CLUSTER NODES

# Cluster 中让相关键落入同一槽（hash tag）
redis-cli -c SET "{order:1001}:status" "paid"
redis-cli -c SET "{order:1001}:amount" "99.00"
```

hash tag 中花括号内的内容相同，键会映射到同一槽。不能为了省事给所有键使用同一个 tag，否则所有数据集中到一个槽，失去分片意义。

### 8.4 易错点和注意事项

- 复制延迟会造成从节点读到旧数据，读写分离前要评估业务是否接受。
- Sentinel 的故障判定和切换需要多个实例协作，部署数量和网络分区策略要经过演练。
- Cluster 不支持跨槽的多键事务和部分多键命令，业务键设计应提前规划。
- 故障切换不是零丢失保证，关键数据仍需结合数据库、持久化和业务幂等设计。

### 8.5 常见问题

**问：主从复制能提高写性能吗？**  
答：通常不能。写仍集中在主节点，从节点主要承担读和备份；写扩展需要分片或其他架构。

**问：Sentinel 和 Cluster 是一回事吗？**  
答：不是。Sentinel 主要解决监控和故障切换；Cluster 解决分片与水平扩展，也包含节点管理，但两者职责不同。

**问：为什么 Cluster 中多键操作会报 CROSSSLOT？**  
答：相关键落在不同哈希槽，无法在单个节点原子执行。可使用 hash tag 让它们同槽，或改写业务避免跨槽操作。

## 9. 分布式锁的实现与注意事项

### 9.1 概念

分布式锁用于在多个进程或多个服务实例之间协调对共享资源的访问。Redis 常用方式是 `SET key token NX PX ttl`：仅当键不存在时设置成功，并携带唯一 token 和过期时间。释放时要原子校验 token 后再删除，避免误删其他持有者的锁。

分布式锁只能降低并发冲突，不能替代数据库唯一约束、幂等设计和业务事务。锁服务本身也可能故障、延迟或发生网络分区。

### 9.2 原理或使用方法

加锁必须原子地完成“存在性检查和设置过期”，不能先 `SETNX` 再单独 `EXPIRE`，否则中间失败会留下永不过期的锁。释放锁使用 Lua 脚本，把比较 token 和删除放在同一原子操作中。

锁的 TTL 要覆盖正常业务执行时间，但过长会在进程崩溃后造成长时间阻塞，过短会在业务未完成时提前释放。自动续期可缓解执行时间不确定的问题，但续期进程也可能暂停或失联。对强一致要求高的场景，可使用 fencing token（单调递增版本）让下游拒绝过期持有者的写入。

### 9.3 示例

```bash
# 加锁：token 必须是每次请求唯一的值
redis-cli SET lock:order:1001 "8f4c2a" NX PX 30000

# 释放：Lua 保证比较 token 与删除是原子操作
redis-cli EVAL "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end" 1 lock:order:1001 "8f4c2a"
```

Lua 脚本返回 1 表示释放成功，0 表示 token 不匹配或锁已不存在。业务层应把 token 保存在请求上下文中，不能使用固定字符串。

### 9.4 易错点和注意事项

- 不要用 `DEL` 直接释放锁而不校验 token，否则可能删掉其他实例后来获得的锁。
- 锁过期后业务仍在执行，可能出现两个持有者同时操作；需要续期、缩短临界区或下游 fencing 校验。
- 单 Redis 实例故障时锁不可用；主从切换可能丢失锁记录。多节点 Redlock 也有争议，不能把它当作无条件强一致保证。
- 不要把锁用于可以靠数据库条件更新解决的高频场景，额外网络往返和锁竞争可能降低吞吐量。

### 9.5 常见问题

**问：为什么加锁和设置过期要一步完成？**  
答：分开执行时，进程可能在两者之间崩溃，导致锁没有过期时间，其他请求永久无法获取。

**问：锁的过期时间应该设多长？**  
答：应覆盖正常临界区耗时并留出余量，同时通过监控和业务拆分缩短临界区。没有适用于所有任务的固定秒数。

**问：有了分布式锁还需要幂等吗？**  
答：需要。锁可能过期、重试可能重复执行，外部调用也可能超时；幂等键和唯一约束能防止重复副作用。

## 10. 常见性能问题与使用误区

### 10.1 概念

Redis 性能问题常见来源包括大键、热键、慢命令、网络往返过多、连接管理不当、持久化 fork 抖动和内存压力。延迟升高不一定由 Redis 命令本身造成，也可能是网络、客户端线程池或下游回源。

大键是单个键的值过大或元素过多；热键是极少数键承受大部分请求。两者都可能导致单节点 CPU、网络或响应时间集中，分片未必能自动解决热键，因为同一个键只能落在某个槽。

### 10.2 原理或使用方法

避免在请求路径执行 `KEYS *`、大范围 `SMEMBERS`、大 Hash `HGETALL`、大 List 全量 `LRANGE` 等可能阻塞或传输大量数据的命令。批量操作可使用 `MSCAN/SSCAN/HSCAN`、Pipeline 或合理分页；Pipeline 减少往返但不会减少服务端实际工作量。

排查时可查看 `INFO`、`SLOWLOG`、`LATENCY`、`MEMORY USAGE`，使用 `redis-cli --bigkeys` 或 LFU 模式下的 `--hotkeys` 做初步分析，再结合业务调用链确认。修改配置或扩节点前应保留基线数据。

### 10.3 示例

```bash
# 查看慢日志和内存概况
redis-cli SLOWLOG GET 10
redis-cli INFO memory
redis-cli INFO stats

# 分析大键（扫描过程有开销，避免高峰执行）
redis-cli --bigkeys

# 渐进式读取大 Hash
redis-cli HSCAN user:1 0 COUNT 100
```

`--bigkeys` 会遍历键空间，数据量大时可能影响性能，应在低峰或副本上评估。`HSCAN` 不能保证一次返回全部字段，需要循环游标。

### 10.4 易错点和注意事项

- Pipeline 不是事务，也不保证命令之间不被其他客户端插入；需要原子性时使用 Lua 或事务，并控制脚本规模。
- 大键删除可使用 `UNLINK` 异步释放，避免 `DEL` 长时间阻塞，但内存释放时机和版本行为需确认。
- 连接池不是越大越好，过多连接会增加内存和上下文切换；应结合服务并发和 Redis 处理能力。
- 持久化、复制和淘汰都可能引起延迟抖动，不能只盯命令执行耗时。

### 10.5 常见问题

**问：Redis 变慢时先看什么？**  
答：先确认延迟范围、慢日志、CPU、内存、网络和持久化指标，再判断是大键、热键、慢命令还是客户端问题。

**问：增加 Redis 节点能解决热键吗？**  
答：不一定。单个热键固定映射到一个槽，除非拆分键或增加本地缓存、读副本等方案，否则扩容不能分散该键的请求。

**问：为什么 Pipeline 能提升吞吐量？**  
答：它把多条命令合并发送，减少网络往返次数；单条命令的服务端执行成本仍然存在，不能替代索引式数据建模或慢命令优化。
