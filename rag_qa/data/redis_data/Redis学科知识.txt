# Redis 学科知识手册

## 1. Redis 的定位与单线程模型

Redis 是基于内存的键值数据库，常被用作缓存、分布式锁、计数器、消息队列、排行榜。它的读写性能高，单机可达十万级 QPS。

核心命令处理是单线程的，因此不存在多线程竞争与上下文切换开销，也不需要为数据结构加锁。单线程仍能很快，原因在于操作都在内存完成，且使用了 I/O 多路复用（epoll）处理大量连接。

Redis 6.0 之后引入多线程处理网络读写，但命令执行仍然是单线程，所以"Redis 单线程"这个说法指的是命令执行模型。耗时命令会阻塞整个实例，例如 keys、大 key 的删除、复杂度高的集合运算，生产环境应当禁用或改写。

## 2. 五种基本数据结构

String 是最基础的类型，可存文本、数字、二进制。常用于缓存对象、计数器（incr）、分布式锁（setnx）。单个 value 上限 512MB。

Hash 是字段到值的映射，适合存对象的多个属性，可以只更新某个字段而不必整体读写。底层在小数据量时用压缩列表，数据量大时用哈希表。

List 是双向链表，支持两端插入弹出，可用于消息队列与最新列表。Set 是无序不重复集合，支持交并差运算，可用于去重与共同好友。ZSet 是有序集合，每个元素带分数，底层用跳表加哈希表，适合排行榜与延时队列。

此外还有 Bitmap、HyperLogLog、GEO、Stream 等扩展类型。

## 3. 持久化 RDB 与 AOF

RDB 是快照，把某一时刻的内存数据以二进制写入磁盘。优点是文件紧凑、恢复快，适合备份与全量同步；缺点是两次快照之间的数据会丢失。

AOF 是追加日志，把每条写命令追加到文件末尾。优点是丢失数据少，可按每秒或每条命令刷盘；缺点是文件大、恢复慢。AOF 重写（rewrite）可以把冗余命令合并，压缩体积。

Redis 4.0 之后支持混合持久化：重写时先写一份 RDB 格式的全量数据，再追加增量命令，兼顾恢复速度与数据完整性。

选择建议：纯缓存可以只开 RDB 或都不开；对数据可靠性有要求时开启 AOF 并设置 appendfsync everysec。

## 4. 过期删除与内存淘汰

设置过期时间用 expire、pexpire、setex。删除策略是惰性删除加定期删除：访问 key 时检查是否过期，过期则删；同时周期性随机抽查一部分设置了过期时间的 key。

惰性加定期仍可能漏掉一些 key，所以需要内存淘汰策略兜底。常见策略：noeviction 不淘汰直接报错；allkeys-lru 从所有 key 中按最近最少使用淘汰；volatile-lru 只淘汰设置了过期时间的；allkeys-random 随机淘汰；volatile-ttl 优先淘汰即将过期的；allkeys-lfu 按访问频率淘汰。

缓存场景通常用 allkeys-lru 或 allkeys-lfu。设置 maxmemory 时必须同时设置淘汰策略，否则内存满后写操作会失败。

## 5. 缓存穿透、击穿、雪崩

穿透指查询不存在的数据，缓存不命中，请求每次都打到数据库。解决方案：缓存空值并设置较短过期时间；用布隆过滤器预先判断 key 是否存在；接口层做参数校验。

击穿指某个热点 key 过期瞬间，大量并发请求同时打到数据库。解决方案：互斥锁，只让一个请求去加载数据，其余等待；热点 key 逻辑过期，后台异步刷新；热点数据预热并设置较长过期时间。

雪崩指大量 key 同时过期或 Redis 整体不可用，导致请求全部压到数据库。解决方案：过期时间加随机偏移，避免同时失效；多级缓存；Redis 集群与哨兵保证高可用；数据库层做限流与熔断降级。

## 6. 分布式锁

分布式锁要满足三个条件：互斥、不死锁、只能由持有者释放。

基础实现是 `set key value nx px 30000`，一条命令同时完成判断不存在与设置过期，避免 setnx 加 expire 不是原子操作的问题。value 要存唯一标识（如 UUID），释放时用 Lua 脚本先比对再删除，防止误删他人的锁。

锁过期而业务未完成时，需要看门狗续期。Redisson 提供了可重入锁与自动续期，生产环境建议直接用成熟客户端而不是手写。

如果对一致性要求极高，要考虑主从切换导致锁丢失的问题，可以用 RedLock 或改用 ZooKeeper、etcd。

## 7. 主从复制与哨兵

主从复制是异步的：从库连接主库后发送 psync，主库执行全量同步生成 RDB 并发送，之后持续发送增量命令。复制是异步的，因此主库宕机可能丢失少量数据。

哨兵（Sentinel）负责监控、通知、自动故障转移。多个哨兵组成集群，通过投票判断主库是否客观下线，然后选一个从库晋升为主库，并通知其他从库切换。

哨兵解决了高可用，但没有解决容量问题：每个节点都存全量数据，写入仍受单机限制。

## 8. Cluster 分片

Cluster 把数据按哈希槽分片，共 16384 个槽，每个主节点负责一部分槽。key 通过 CRC16 计算后对 16384 取模决定所属槽。

客户端访问任意节点，如果 key 不在该节点，会返回 MOVED 重定向到正确节点。集群至少需要三个主节点，通常配三个从节点实现高可用。

跨槽操作受限：涉及多个 key 的命令要求这些 key 在同一个槽，可以用 hash tag（如 `user:{1001}:name`）把相关 key 固定到同一槽。事务与 Lua 脚本也只能作用于同槽 key。

## 9. 事务与 Lua

Redis 事务用 multi 开启、命令入队、exec 执行。它不保证原子回滚：如果某条命令运行时出错，其余命令仍会执行，只是错误会被记录。因此 Redis 事务更像是批量执行，不是关系数据库意义上的事务。

Lua 脚本在服务端原子执行，期间不会插入其他命令，适合实现"读取-判断-写入"的复合逻辑，例如分布式锁释放、库存扣减。

注意 Lua 脚本执行时间过长会阻塞整个实例，应当保持脚本简短。Redis 7 之后可以用 Function 管理脚本，避免每次传输脚本内容。

## 10. 缓存一致性

先更新数据库再删除缓存（Cache Aside）是最常用的方案。不推荐先删缓存再更新数据库，因为并发下可能把旧值写回缓存。

删除缓存仍可能不一致：读请求在缓存失效后回源，读到旧数据并写回，此时若更新已完成，缓存就是旧的。常见缓解手段是延迟双删、设置较短的过期时间、用 binlog 订阅（Canal）异步刷新缓存。

强一致需要引入分布式锁或串行化，成本高。多数业务接受最终一致，关键是给出可接受的过期时间并监控不一致率。

## 11. 常见性能问题

大 key：单个 value 过大或集合元素过多，会导致删除阻塞、网络拥塞、集群倾斜。应拆分大 key，用 hscan、sscan 渐进式遍历，删除用 unlink 异步释放。

热 key：某个 key 访问量极高，打满单个节点。可以做本地缓存、把 key 打散成多个副本、限流。

慢查询：避免 keys、flushall、大范围 zrange、复杂度高的集合运算。用 slowlog 定位，阈值按业务设置。

连接数过多：使用连接池，避免短连接频繁创建。关注 blocked_clients 与 rejected_connections 指标。

## 12. 使用规范

key 命名采用业务前缀加冒号分隔，如 `order:1001:detail`，便于排查与批量操作。合理设置过期时间，避免无过期 key 堆积。

value 控制在合理大小，String 建议不超过 10KB，集合元素数量控制在千级以内。避免在生产环境使用 keys 与 flushall。

持久化与淘汰策略要显式配置。重要数据不能只依赖 Redis，要有数据库兜底与重建方案。上线前压测，明确 QPS 与内存上限，配置告警。
